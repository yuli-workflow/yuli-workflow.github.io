Privacy Policy

Yuli Email Ops  ·  Last updated: 25 October 2026

1. Overview

Yuli Email Ops ("the application") is a private, non-commercial tool operated by a single individual ("the owner") for the owner's own Gmail mailboxes. Its purpose is to reduce the number of messages the owner has to read personally each day, by sorting them into priority categories and pulling out details such as deadlines, amounts and renewal dates.

The application is not offered to the public. It has no sign-up, no user accounts, no backend server, and no other users. The only person who authorises it, and the only person whose mailboxes it reads, is the owner.

This policy describes what the application does, and names every third party that receives or stores data derived from those mailboxes. Where the application relies on controls rather than guarantees, this policy says so.

2. What the application accesses

The application holds three separate authorisations for each mailbox. Each is stored as its own token, and each program uses only the token for its own task.

ScopeUsed forWhat the code allows
gmail.readonly Daily triage, account migration, and reading messages the owner has labelled (section 4) Reading only. Google itself rejects any change made with this token.
gmail.modify Adding the owner's own sorting labels Adding labels from a fixed list of five owner-created labels (for example "keep: receipt" or "move to main inbox"). Nothing else.
gmail.compose Preparing reply drafts for the owner to review Creating drafts only. The draft is left in the owner's Drafts folder; sending is done, if at all, by the owner by hand.

Stated limits. Google does not offer a "labels only" or "drafts only" scope. gmail.modify technically permits archiving, trashing and removing labels, and gmail.compose technically permits sending. The application's code does not expose those operations: every outgoing request is checked against an allow-list of endpoints and request bodies, and anything else is refused before it is sent. This is a control in the application's code, not a restriction enforced by Google.

Using these scopes, the application reads from the owner's own mailboxes:

  • Message headers: sender, recipients, subject, date, unsubscribe header
  • Message bodies, in plain text
  • Attachment file names, media types and sizes — attachment contents are not downloaded
  • Gmail label identifiers and read/unread status

All of the above is read into the memory of a program running on the owner's computer. Section 4 describes which parts of it then leave that computer, and which do not.

3. How the data is used

The data is not used for any other purpose.

4. Where the data goes

Processing is split between the owner's computer and a remote service. The split is the most important thing in this policy, so it is set out stage by stage.

Stage 1 — Retrieval and extraction (owner's computer)

A program on the owner's computer calls the Gmail API, holds the response in memory, removes the categories of data listed in section 6, and then converts each message into a structured record. The full text of the message is not carried forward into that record.

Stage 2 — Classification (remote, Anthropic PBC)

The structured records are sent to Claude, a large language model operated by Anthropic PBC, which assigns each record a priority category and a suggested action type. The following table states exactly what is and is not included in what is sent.

Sent to AnthropicNot included in what is sent
  • A per-run pseudonymous identifier for each message (e.g. MSG-0007)
  • A pseudonymous identifier for each sending service (e.g. SVC-017)
  • A service category label from a fixed list (for example bank, ecommerce, saas)
  • A message type label from a fixed list (for example invoice, security-alert)
  • Labels from a fixed list of signals observed in the message (for example payment_failed, renewal_upcoming)
  • Monetary amounts as numbers, with ISO currency codes
  • Dates in normalised form, with a role such as deadline or renewal
  • Counts: number of attachments, number of links, message length
  • Statistics about how many items were removed at stage 1, by category code
  • True/false flags such as unread status and presence of an unsubscribe header
  • Message bodies
  • Subject lines
  • Excerpts, snippets or quotations of message text
  • Sender display names, sender email addresses and sender domains
  • Recipient addresses
  • Attachment file names
  • Gmail label names
  • Any other free-form text originating from a message

What this does and does not mean. Message text does not leave the owner's computer as part of normal operation. Information about messages does: in particular, monetary amounts, dates, and the fact that a pseudonymous service falls into a category such as bank. That is personal data about the owner, and it is processed on infrastructure operated by Anthropic PBC.

Records that the program cannot convert into a reliable structured form are marked for the owner to read personally and are not sent at all.

Stage 3 — Summary rendering (owner's computer)

The pseudonymous identifiers are matched back to real service names on the owner's computer, using a lookup table that is held locally, and the daily summary is assembled there. That summary is not sent back to Anthropic.

Exception — Messages the owner labels personally

Stages 1 to 3 describe the daily triage. Separately, the owner can apply a label in Gmail to an individual message to ask for it to be handled. Messages labelled this way are processed differently, and the difference is set out here in full.

Owner's labelSent to AnthropicWritten elsewhere
Newsletter to study The full subject line and body of that one message. Notes on writing structure, kept on the owner's computer.
Class or event notice The full subject line and body of that one message. One event in the owner's Google Calendar: title, time, meeting link as written in the message, and a note of where the notice came from.
Subscription receipt Not the message text. A structured record only (service name, amount, currency, dates, billing cycle, plan name), checked against an allow-list before it is sent. One row in the owner's subscription tracker in Notion with the same fields. Card numbers and card last-four digits are never written.

What this means. For the first two labels, the complete text of the labelled message, including anything written in it about other people, is processed on infrastructure operated by Anthropic PBC. Only messages the owner has labelled one by one are read this way: the program reads one message at a time, by its identifier, and refuses any message that does not carry the matching label. Links in the message are copied as text and are not opened.

6. What is removed before data leaves the computer

Before anything is sent, the program removes the following from the material it works with, replacing each with a marker:

  • One-time passcodes, verification codes and passwords
  • API keys, tokens and similar credentials
  • Query strings and long paths in URLs, which can act as sign-in links
  • National identity numbers, passport numbers, telephone numbers and street addresses
  • Full card numbers, card last-four digits and bank account numbers
  • Invoice, order and transaction reference numbers
  • The email local part of any address (the portion before the @)

Because the structured records described in section 4 contain no free-form text fields, text that this step fails to catch still has no field in which it could be transmitted. The removal step is a second line of defence, not the only one. This does not apply to messages the owner labels as a newsletter to study or a class notice: their full text is read as described in section 4.

Stated limits. The removal step uses pattern matching, not comprehension, and will not recognise every possible way of writing a sensitive value. Names of third parties appearing inside messages cannot be reliably detected. The controls described in this policy reduce exposure; they do not eliminate it, and this policy does not claim that they do.

9. Security

  • OAuth tokens are stored outside the application's source directory and are excluded from version control by configuration.
  • Each task uses its own token with the narrowest scope that meets its purpose, and checks at runtime that the token carries no broader permission, refusing to run if it does.
  • Requests that change anything in Gmail are checked against an allow-list of endpoints and request bodies; sending, trashing, archiving and removing labels are refused before any request is made.
  • Outbound records are checked against a schema and a value-level allow-list before they are sent; records that fail are not sent.
  • The component that performs classification is configured without file system or network access, so that instructions embedded in a message cannot cause it to take an action.
  • Links contained in messages are not opened or followed by the application.
  • Attachment contents are not downloaded or opened.

10. Retention and deletion

Summaries, the lookup table and any retained raw output are files on the owner's computer and can be deleted by the owner at any time. Deleting them removes the local copy only. It has no effect on any copy held by a party named in section 5, whose retention is governed by that party's own terms.

11. Revoking access

The owner can withdraw the application's access at any time by either:

  • removing "Yuli Email Ops" at myaccount.google.com/permissions; or
  • deleting the locally stored token files.

Either action stops further access.

12. Data subjects

The owner is the sole user and the primary data subject. No other person's mailbox is accessed. Messages in the owner's mailboxes may nonetheless contain information about the people and organisations that sent them; section 6 describes what is removed from that material before anything is sent, and the limits of that removal.

13. Children

The application is used solely by its adult owner and is not directed to children.
